    Stratégie d'Upload de Texture Asynchrone¶

    Ce document détaille l'implémentation du système d'upload asynchrone de textures haute résolution dans suckless-ogl, en se concentrant spécifiquement sur la stratégie de Pixel Buffer Object (PBO) à double tampon utilisée pour éliminer les blocages du thread principal, et la stratégie d'initialisation de ressources multi-images qui répartit les coûts d'allocation GPU sur plusieurs images (frames).

    Le Problème¶

    L'upload de grandes textures HDR 4K (environ 64 Mo) vers le GPU est une opération lourde.

    • Upload Direct (glTexImage2D) : Bloque le pilote et le thread principal jusqu'à ce que la copie soit terminée (~50ms+), provoquant des chutes de framerate massives.
    • PBO Naïf : L'utilisation d'un seul PBO permet un transfert DMA asynchrone, mais le mappage de ce PBO (glMapBufferRange) peut toujours bloquer si le GPU est en train d'y lire (synchronisation implicite).
    • Upload Monolithique : Même avec des PBOs, effectuer tout le travail GPU (allocation du stockage de texture, upload des données, génération des mipmaps) en une seule image crée un pic de ~60ms.

    La Solution : PBOs Double Tampon Non Synchronisés¶

    Pour garantir que le Thread Principal n'attende jamais le GPU, nous utilisons une stratégie de Ping-Pong avec deux PBOs persistants.

    Architecture¶

    1. Thread Worker Asynchrone :

      • Charge le fichier HDR depuis le disque (I/O).
      • Décode vers un buffer de floats.
      • Attend que le Thread Principal fournisse un pointeur GPU mappé.
      • Convertit Float -> Half-Float (FP16) directement dans la mémoire mappée.

    2. Thread Principal (env_manager_update) :

      • Vérifie si le worker est en attente.
      • Sélectionne le prochain PBO disponible (index upload_pbo_idx).
      • Mappe le PBO avec le flag GL_MAP_UNSYNCHRONIZED_BIT.
      • Transmet le pointeur au worker.
      • Lorsque le worker a terminé, démappe (Unmap) et appelle glTexSubImage2D (dans les étapes de chargement progressif IBL/chargement).

    Optimisations Clés¶

    1. Double Tampon & Mappage Non Synchronisé¶

    En alternant entre upload_pbo[0] and upload_pbo[1], nous garantissons que pendant que le GPU lit depuis le PBO 0 (pour la texture précédente), nous mappons et écrivons dans le PBO 1. Cela nous permet d'utiliser le flag GL_MAP_UNSYNCHRONIZED_BIT, qui indique au pilote : "Je promets que je n'écrase pas des données que tu es en train d'utiliser, donc ne vérifie rien, donne-moi juste le pointeur immédiatement."

    2. Allocation Persistante (Sans Orphelinage)¶

    Auparavant, nous utilisions glBufferData(NULL) (Orphelinage/Orphaning) pour forcer le pilote à nous donner un nouveau bloc de mémoire. Bien que cela évite la synchronisation, l'allocation elle-même pour 64 Mo prenait ~26-40ms sur certains pilotes. Approche Actuelle : Nous allouons les PBOs une seule fois (ou les redimensionnons uniquement si des textures plus grandes sont chargées). Nous réutilisons le stockage VRAM existant, éliminant ainsi le coût d'allocation.

    3. Upload en 2 étapes¶

    Au lieu de faire la conversion complète sur le thread spécifique puis de copier, nous faisons :

    1. Chargement (Worker)
    2. Mappage (Thread Principal via EnvManager)
    3. Conversion & Écriture (Worker, directement dans le PBO)
    4. Upload (Thread Principal, DMA)

    Cela évite que le Thread Principal ne touche aux données de pixels sur le CPU, et évite au Worker d'avoir besoin d'un contexte GL.

    Initialisation Multi-Images de Ressources¶

    Le Goulot d'Étranglement¶

    Même avec la stratégie PBO ci-dessus, l'image d'upload causait toujours un pic de ~60ms car toutes les opérations GPU lourdes étaient concentrées sur une seule image :

    Opération Coût Approx. Cause
    glTexStorage2D (13 niveaux de mip) ~15-20ms Allocation VRAM de ~85 Mo
    glUnmapBuffer ~1-3ms Flush du cache d'écriture DMA
    glTexSubImage2D ~10-15ms Transfert DMA PBO → texture
    glGenerateMipmap ~10-15ms Calcul GPU sur 13 niveaux
    glGetError × 3 ~5-10ms Points de synchronisation GPU (blocages)
    Total ~45-65ms Pic sur une seule image

    La Stratégie : Répartir le Travail sur 3 Images¶

    Au lieu de tout faire en une seule image, nous distribuons le travail en utilisant le protocole multi-étapes du chargeur asynchrone comme frontières naturelles d'images :

    gantt
    title Répartition Temporelle des Images
    dateFormat X
    axisFormat %s ms

    section Avant (1 image)
    Configuration PBO + Stockage + Upload + Mipmaps + 3×glGetError :done, 0, 60

    section Après (3 images)
    Image N   - Config PBO & Mappage     :active, 0, 5
    Image N+1 - Préalloc VRAM (niveau 0) :active, 8, 15
    Image N+M - Upload + Mipmaps         :active, 18, 38

    Image N : Configuration du PBO (ASYNC_WAITING_FOR_PBO)¶

    // env_manager_update() — branche ASYNC_WAITING_FOR_PBO
texture_ensure_pbo(&mgr->upload_pbo[pbo_idx], &mgr->upload_pbo_size[pbo_idx], size);
void* ptr = texture_map_pbo(mgr->upload_pbo[pbo_idx], size);
async_loader_provide_pbo(loader, ptr, mgr->upload_pbo[pbo_idx]);

// Planifier la pré-allocation différée pour l'image SUIVANTE
mgr->pending_prealloc_w = req.width;
mgr->pending_prealloc_h = req.height;

    Coût : ~1-5ms (réutilisation du PBO, pas d'allocation)

    Image N+1 : Pré-allocation VRAM Différée¶

    // env_manager_update() — haut de la fonction, avant le poll
if (mgr->pending_prealloc_w > 0) {
    scene->gpu->recycled_hdr_tex = texture_preallocate_hdr(
        mgr->pending_prealloc_w, mgr->pending_prealloc_h,
        scene->gpu->recycled_hdr_tex);
    mgr->pending_prealloc_w = 0;
    mgr->pending_prealloc_h = 0;
}

    Décisions clés :

    • glTexImage2D au lieu de glTexStorage2D : Alloue uniquement le niveau 0 (~64 Mo) au lieu des 13 niveaux de mipmaps (~85 Mo). La chaîne de mipmaps est créée plus tard par glGenerateMipmap.
    • Pas de glGetError() : Évite de forcer un point de synchronisation GPU. Les erreurs sont capturées par le callback GL_DEBUG_OUTPUT_SYNCHRONOUS.
    • Réutilisation de texture : Si recycled_hdr_tex correspond déjà aux dimensions et au format, la pré-allocation est un no-op (chemin à coût nul).

    Coût : ~5-15ms au premier chargement, ~0ms sur les chargements suivants avec les mêmes dimensions.

    Image N+M : Upload depuis le PBO (ASYNC_READY)¶

    // env_manager_process_loading_step_internal() étape EML_UPLOAD_HDR_FROM_PBO
// texture_upload_hdr_from_pbo() est appelée
// reuse_tex_id correspond à la texture pré-allouée -> sauter glTexStorage2D (OK)
glUnmapBuffer(PBO);
glTexSubImage2D(..., 0);   // DMA depuis PBO offset 0
glGenerateMipmap();        // Génère la chaîne de mipmaps (alloue aussi les niveaux restants)

    Coût : ~20-30ms (travail GPU incompressible)

    Suppression des Points de Synchronisation (Audit glGetError)¶

    Pourquoi glGetError() Bloque le Pipeline¶

    glGetError() est une requête synchrone : le CPU doit attendre que le GPU ait traité toutes les commandes en attente avant de renvoyer l'état d'erreur. Dans une architecture en pipeline, cela va à l'encontre de l'intérêt des chargements asynchrones.

    Le Filet de Sécurité : GL_DEBUG_OUTPUT_SYNCHRONOUS¶

    L'application active la sortie de débogage OpenGL en mode synchrone (gl_debug.c) :

    glEnable(GL_DEBUG_OUTPUT);
glEnable(GL_DEBUG_OUTPUT_SYNCHRONOUS);

    Cela signifie que chaque erreur GL est déjà signalée immédiatement via le callback de débogage, rendant les appels à glGetError() redondants pour la détection d'erreurs.

    Évolution de l'Implémentation¶

    Phase 1 : Asynchrone Naïf (Bloquant)¶

    Au départ, le worker convertissait les données dans un buffer CPU, et le Thread Principal appelait glBufferData.

    • Résultat : Le thread principal bloquait pendant ~45ms lors de l'allocation/copie.

    Phase 2 : PBO Unique + Orphelinage (Ralentissements)¶

    Nous sommes passés aux PBOs, mais en réutilisant un seul PBO. Nous avons essayé de forcer glBufferData(NULL) pour orpheliner le buffer.

    • Résultat : La configuration du PBO allouait de la mémoire à chaque image, prenant ~26-40ms. Le temps de rendu a explosé.

    Phase 3 : PBO Unique + Synchronisation (Bloquant)¶

    Nous avons essayé de supprimer l'orphelinage.

    • Résultat : glMapBufferRange bloquait fortement car le GPU lisait encore l'upload précédent. La synchronisation implicite s'est activée.

    Phase 4 : Double Tampon Persistant (Stratégie Précédente)¶

    Nous avons implémenté upload_pbo[2].

    • Résultat : Le coût de configuration du PBO est tombé à < 0.1ms. Le blocage a complètement disparu, et nous maintenons le streaming HDR 4K à plein framerate.

    Phase 5 : Pré-allocation Multi-Images & Retrait de glGetError (Actuelle)¶

    Nous avons divisé l'initialisation des textures sur 3 images et supprimé les points de synchronisation de glGetError().

    • Config PBO à l'image N (~1-5ms)
    • Pré-allocation VRAM différée à l'image N+1 (~5-15ms, ou 0ms avec réutilisation)
    • Upload + Mipmaps à l'image N+M (~20-30ms)
    • 3 points de synchronisation glGetError() supprimés du chemin d'upload
    • glTexImage2D(level 0) remplace glTexStorage2D(13 levels) : allocation plus légère, création de mipmap différée

    Résultat : Le pic d'image dans le pire des cas est passé de ~60ms à ~20-30ms. Avec la réutilisation de texture (mêmes dimensions), l'image de pré-allocation est un no-op.

    Readbacks de Performance Asynchrones (Exposition & Histogramme)¶

    Le même principe de PBO est appliqué en sens inverse pour les lectures GPU vers CPU (Auto-Exposition et Histogramme).

    Le Défi¶

    glReadPixels ou glGetTexImage sans PBO bloquera le CPU jusqu'à ce que le GPU termine le rendu de l'image et transfère les données. Cela coûte généralement 1-2ms par appel, même pour de petites données.

    L'Implémentation¶

    Nous utilisons des PBOs Double Tampon + Clôtures de Synchronisation (Sync Fences) :

    1. Phase de Déclenchement (Image N) :
    2. Appeler glGetTexImage dans le pbo[idx].
    3. Insérer une clôture : sync[idx] = glFenceSync(GL_SYNC_GPU_COMMANDS_COMPLETE, 0).
    4. Phase de Lecture (Image N+1) :
    5. Vérifier la clôture : glClientWaitSync(sync[!idx], ..., 0).
    6. Si GL_ALREADY_SIGNALED ou GL_CONDITION_SATISFIED, mapper le PBO et lire les données.
    7. Si non signalée, sauter la mise à jour pour cette image. Cela évite que le CPU ne bloque, au coût d'une image de latence supplémentaire pour les valeurs de l'interface.

    Résultat : Le calcul de l'exposition et l'extraction de l'histogramme coûtent < 0.05ms sur le CPU, quelle que soit la complexité de la scène.

    Références du Code¶

    • src/app.c : Appelle env_manager_update dans app_update.
    • src/env_manager.c : Gère la boucle de PBOs, la pré-allocation différée dans env_manager_update, et le pilotage des étapes de chargement progressif. Champs : pending_prealloc_w, pending_prealloc_h, upload_pbo[2], upload_pbo_size[2], upload_pbo_idx.
    • src/texture.c : texture_ensure_pbo (dimensionnement), texture_map_pbo (flags), texture_preallocate_hdr (pré-allocation VRAM), texture_upload_hdr_from_pbo (pipeline d'upload).
    • src/async_loader.c : Gère la machine à états de threads (WAITING_FOR_PBO).
    • include/env_manager.h : La structure EnvManager contient pending_prealloc_w/h, upload_pbo[2], upload_pbo_size[2], upload_pbo_idx.
    • src/gl_debug.c : Configure GL_DEBUG_OUTPUT_SYNCHRONOUS.
