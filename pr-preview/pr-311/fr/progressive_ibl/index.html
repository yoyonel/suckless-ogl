    Architecture IBL Progressive & Asynchrone¶

    Ce document détaille l'implémentation du chargement asynchrone et de la génération progressive des cartes IBL (Image Based Lighting) pour éliminer les saccades et les gels lors du changement d'environnement.

    1. Vue d'Ensemble¶

    L'objectif était de passer d'un chargement synchrone bloquant (gel de 100ms à 800ms) à une approche fluide où le temps de calcul est réparti sur plusieurs images (Time Slicing).

    Le Pipeline¶

    1. Chargement Disque (Thread Séparé) : Le fichier .hdr est chargé et décodé (stb_image) dans un thread dédié (async_loader.c).
    2. Upload GPU (Thread Principal) : Une fois prêt, les données brutes sont uploadées vers la VRAM (texture HDR) en arrière-plan à l'aide de PBOs double tampon.
    3. Génération IBL (Progressive) : Une machine à états (env_manager_update_ibl_state) pilote les compute shaders étape par étape pour générer :
      • La luminance moyenne (lecture GPU asynchrone via glFenceSync).
      • La carte d'irradiance (diffuse).
      • La carte spéculaire pré-filtrée (réflexion).
    4. Échange (Double Buffering) : Nous utilisons des textures temporaires "Pending". L'ancien environnement reste affiché jusqu'à ce que le nouveau soit prêt à 100%.

    2. Stratégie de Découpe ("Slicing")¶

    Les compute shaders PBR (particulièrement pour les cartes spéculaires haute résolution) sont très coûteux. Le calcul d'une texture complète 512x512 prend environ 250ms sur un GPU intégré, gelant l'application.

    Solution : Découper le travail horizontalement ("Slicing") et ne calculer qu'une bande de l'image par frame.

    2.1 Protection contre le Chevauchement (Crucial)¶

    Les Workgroups des Compute Shaders ont une taille fixe (32x32). Si nous demandons de calculer une tranche de 1 pixel de haut, le GPU lance quand même un bloc de 32 pixels de haut. Sans protection, les 31 lignes excédentaires écrasent/recalculent les pixels voisins, gaspillant massivement les ressources.

    Le Correctif (u_max_y_slice) : Nous passons une limite précise au shader :

    // shaders/IBL/spmap.glsl & irmap.glsl
uniform int u_max_y_slice; // Limite Y de la tranche actuelle

void main_task() {
    // ...
    // Arrêt chirurgical pour éviter les workgroups gaspillés sur les bords de tranche
    if (pixel_pos.y >= u_max_y_slice) return; // Arrêt immédiat pour les threads fantômes
    // ...
}

    3. Configuration Optimisée (Slicing Adaptatif)¶

    Pour concilier fluidité (pas de gel) et vitesse globale (chargement rapide), nous utilisons une stratégie adaptative basée sur la charge de travail, combinée à des lectures GPU asynchrones.

    A. Luminance Moyenne (Lecture Asynchrone)¶

    Le calcul de la luminance moyenne est nécessaire pour ajuster automatiquement la luminosité, mais la lecture du résultat vers le CPU peut provoquer un blocage important du pipeline (glGetBufferSubData).

    • Stratégie : Lecture asynchrone.
    • Implémentation : Nous exécutons le compute shader et insérons une clôture glFenceSync. La machine à états passe à IBL_STATE_LUMINANCE_WAIT. Dans les images suivantes, glClientWaitSync(..., 0) est utilisé pour interroger le GPU de manière non bloquante. Dès que les données sont prêtes, nous les lisons instantanément sans bloquer le CPU.

    B. Génération de Mipmaps (glGenerateMipmap)¶

    Avant de commencer le calcul de l'IBL, la texture HDR uploadée doit avoir sa chaîne de mipmaps générée.

    • Stratégie : Image isolée (Dedicated Frame).
    • Coût : ~40ms (sur une image HDR 4K).
    • Limitation : glGenerateMipmap est une fonction OpenGL monolithique. Elle ne peut être ni découpée ni interrompue. Elle force le GPU à lire, réduire et écrire 13 niveaux de données flottantes haute précision en une seule opération massive.
    • Résultat : Cela crée un seul pic de rendu incompressible (~24 FPS pendant une seule image). Cette étape est volontairement isolée sur sa propre image pour éviter de s'accumuler avec l'upload (glTexSubImage2D) ou les compute shaders IBL.

    C. Carte d'Irradiance (64x64)¶

    • Stratégie : Découpage constant.
    • Découpage : 12 tranches (Slices).
    • Coût : ~5ms / tranche.

    D. Carte Spéculaire (1024x1024)¶

    C'est la partie la plus lourde. Le coût par niveau de mipmap diminue de manière exponentielle.

    Niveau Mip Taille Stratégie Coût Est. / Image Description
    Mip 0 1024x1024 24 Tranches ~25-35ms Le plus lourd (détails haute fréquence).
    Mip 1 512x512 8 Tranches ~15-25ms Moyen.
    Mip 2 256x256 1 Tranche ~15ms Léger, calculé d'un seul coup.
    Mip 3-10 128..1 Regroupement Final ~20ms (Total) Tous calculés dans une seule image.

    Regroupement Final (Tail Grouping) : Regrouper les petits mips (3 à 10) évite de gaspiller 7 images de latence pour des tâches minuscules (<1ms chacune).

    4. Optimisation de la Barrière de Mémoire Différée¶

    4.1 Le Problème : Coût des Barrières par Tranche¶

    Initialement, chaque exécution de tranche appelait glMemoryBarrier(GL_ALL_BARRIER_BITS) à la fin. Cela forçait le GPU à :

    1. Vider tout le pipeline — toutes les commandes en cours doivent se terminer avant le début de la tranche suivante.
    2. Invalider tous les caches GPU — cache de texture, L2, framebuffer, etc.
    3. Redémarrage à froid — l'exécution suivante doit récupérer env_hdr_tex depuis la VRAM au lieu d'utiliser le cache.

    Le surcoût était super-linéaire : doubler le nombre de tranches doublait plus que le temps total de traitement. Cela rendait un découpage fin (beaucoup de petites tranches pour un budget de ~33ms/image) impraticable.

    4.2 Observation Clé : Pas de Dépendance entre les Tranches¶

    L'analyse du flux de données révèle que les tranches sont indépendantes :

    Tranche 0: LIRE env_hdr_tex → ÉCRIRE dest_tex[mip][y: 0..N]
Tranche 1: LIRE env_hdr_tex → ÉCRIRE dest_tex[mip][y: N..2N]
...etc
    • Toutes les tranches lisent à partir de la même texture HDR source (jamais modifiée).
    • Chaque tranche écrit dans une plage Y disjointe de la texture de destination.
    • Il n'y a pas de risque de conflit lecture-après-écriture ou écriture-après-écriture entre les tranches.

    Il en va de même pour les niveaux de mipmaps : chaque mip écrit dans un niveau de mip différent de la destination, et lit depuis la même texture HDR source.

    4.3 Solution : Une Unique Barrière Différée¶

    Supprimer toutes les barrières par tranche et émettre une seule barrière à la toute fin :

    • pbr_prefilter_mip() et pbr_irradiance_slice_compute() n'appellent plus glMemoryBarrier(). C'est le code appelant qui s'en charge.
    • Une unique barrière glMemoryBarrier(GL_SHADER_IMAGE_ACCESS_BARRIER_BIT) est placée dans env_manager_update_ibl_state lors du passage à l'état IBL_STATE_DONE, juste avant que les textures ne soient échantillonnées pour le rendu.
    • Le type de barrière est réduit de GL_ALL_BARRIER_BITS à GL_SHADER_IMAGE_ACCESS_BARRIER_BIT — seule la cohérence entre l'écriture d'image et la lecture de texture est synchronisée.

    4.4 Résultats de Benchmark (16 tranches sur Mip 0)¶

    Métrique Avant (barrière par tranche) Après (différée) Amélioration
    Moyenne ~1004 ms ~875 ms ~13%
    Minimum 792 ms 668 ms ~16%
    Maximum 1189 ms 904 ms ~24%
    Variance ±200 ms ±80 ms Beaucoup plus stable

    La réduction de la variance est importante : les vidages de pipeline par tranche introduisaient des temps d'inactivité GPU imprévisibles. Avec la barrière différée, le GPU fonctionne en continu sans interruption.

    [!IMPORTANT] Avec la barrière différée, le nombre de tranches peut être augmenté librement sans surcoût super-linéaire. Cela permet de viser précisément un budget de ~33ms/image par tranche pour maintenir un framerate de 30 FPS fluide pendant la génération de l'IBL.

    5. Performances Globales¶

    Avec cette architecture sur un GPU dédié :

    • FPS : Reste fluide (~30+ FPS pendant la génération IBL).
    • Temps Total : Une transition complète d'environnement prend environ 850ms à 950ms (avec 24+8+12 tranches).
    • Latence Perçue : Presque nulle grâce à l'affichage continu de l'ancien environnement pendant le calcul.

    6. Fichiers Clés¶

    • src/env_manager.c : Contient la machine à états de la génération progressive d'IBL et met à jour les transitions.
    • src/pbr.c : Implémente le calcul découpé (pbr_prefilter_mip, pbr_irradiance_slice_compute) — aucune barrière interne.
    • include/pbr.h : Documentation de l'API avec la mention @note sur la responsabilité de la barrière par l'appelant.
    • shaders/IBL/*.glsl : Shaders modifiés pour supporter u_offset_y et u_max_y.
